# Kisht: план продолжения для Cursor

## Цель

Понятный инструмент фермера в Таджикистане: участок → условия и дата посева →
загрузка реальных источников → объяснимая симуляция → сравнение с рекомендованным планом.
Три рабочих раздела и отдельная «Демо симуляция». Русский и английский, английское название Kisht.
Не добавлять панели и кнопки без конкретного решения для фермера.

## Запуск и структура

Рабочая папка: `C:\Users\user\Desktop\nasa\kisht`.

```powershell
npm ci
npm run dev
npm test
npm run build
```

React 19, TypeScript, Vite; Leaflet для участка; Three.js / React Three Fiber для сцены;
серверные обработчики в `worker/`, конфигурация разработки в `vite.config.mjs`.
Секреты только в игнорируемом `.env.local` или серверном окружении, по `.env.example`.
Не копировать API-ключи в клиент, документы, логи и коммиты.

Сначала прочитать AUDIT_REPORT.md и текущий код: в проекте уже расширен список культур,
поэтому старые документы про поддержку только пшеницы не считать актуальным контрактом.

## Фаза 1 — закончить проверку пользовательского сценария

1. Пройти чистый запуск без сохранённого участка: выделение контура, сохранение, культура, дата, вода.
2. Проверить загрузку реальных NASA, SRTM и прогноза: время, источник, статус каждого сервиса.
3. При отказе источника показывать конкретную ошибку и повтор загрузки; не подставлять синтетические значения.
4. Проверить изменение поля/культуры/даты во время запроса: старый ответ не должен стать текущим.
5. Проверить применение рекомендаций: дата, доза и календарь совпадают с рассчитанным вариантом.

Готово, если весь путь проходит без ручных исправлений; отключение любого сервиса не приводит к ложным результатам.

## Фаза 2 — точность модели и происхождение данных

1. Инвентаризировать все профили: источник, коэффициенты, продолжительность стадий, корни, температурные пороги.
2. Разделить подтверждённые коэффициенты и допущения; перепроверить таблицы FAO по первоисточникам.
3. Добавить тесты водного баланса и длительности для каждой культуры, включая вызов без явного профиля.
4. Проверить согласованность выбранного типа почвы и доступной влаги в расчёте и рекомендациях.
5. Явно различать исторический сценарий, ближайший прогноз и модельные предположения.

Готово, если каждый результат можно объяснить через входные данные, формулу и источник.
Не утверждать «точно вырастет», «замёрзнет» или величину урожая без отдельной проверенной модели.

## Фаза 3 — полезные рекомендации

1. Показывать период поиска и годы исторической выборки.
2. Сравнивать текущую дату с предложенной по воде, холоду и жаре; объяснять причину выбора.
3. Показывать разброс по годам, а не только одну центральную оценку.
4. Учитывать доступную воду и метод полива; отделять исторический план от оперативного назначения по прогнозу.
5. Одна основная кнопка применения, затем сразу симуляция с новым планом и возможностью возврата.

Готово, если пользователь понимает, что изменится, почему и какие риски остаются.

## Фаза 4 — объяснимая 3D-сцена

1. Привязать каждое визуальное состояние к показателю выбранного дня.
2. Различать стадии культур геометрией, а не только цветом.
3. Показать поступление воды, влажность корневого слоя и дефицит без визуального обещания точной физики.
4. Нажатие на риск переводит на соответствующий день и раскрывает причину и возможное действие.
5. Настроить качество по устройству, повторное использование геометрии/материалов, проверить память и FPS.

Готово, если фермер может объяснить состояние сцены по карточке дня; отказ WebGL оставляет доступными цифры и действия.

## Фаза 5 — помощник

1. Проверить реальные текстовые и фото-запросы, отмену, ошибки и ограничения провайдера.
2. Сохранять историю при переключении модели; тестировать исчерпание всех резервов и честную ошибку.
3. Фото даёт предварительные признаки и уточняющие вопросы, не точный химический состав почвы.
4. Предложения меняют настройки только по явному нажатию; устаревший контекст блокирует применение.
5. Перед публичным доступом добавить устойчивые серверные лимиты и бюджет, а не только ограничения внутри процесса.

Готово, если чат помогает пользоваться расчётом, не выдумывает погоду и не скрывает недоступность API.

## Фаза 6 — интерфейс и доступность

1. Проверить RU/EN на 320/360/390/768/1024/1440 px, раскрытые блоки и длинные ответы.
2. Проверить zoom 200%, клавиатуру, видимый фокус, подписи полей, экранный диктор.
3. Проверить мобильную экранную клавиатуру: закрытие и отправка чата всегда доступны.
4. Свести дубли CSS в компоненты постепенно, сохранив правила responsive.css и отсутствие переполнения.
5. Не маскировать дефекты глобальным overflow-x:hidden.

Готово, если все основные действия доступны без горизонтального скролла страницы;
локальный скролл допустим для длинной таблицы и ряда прогноза.

## Фаза 7 — выпуск и демонстрация

1. Запустить тесты, сборку и аудит зависимостей; документировать оставшиеся предупреждения.
2. Проверить production-сервер: API-маршруты, переменные окружения, кеш, повторные запросы.
3. Подготовить короткий показ: участок → данные → риск → предложение → сравнение.
4. В демо всегда видна маркировка синтетической погоды. Рабочие данные и демо не смешиваются.
5. Опубликовать проверенную версию, затем повторить основной сценарий на её URL.
